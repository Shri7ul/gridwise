## Key decisions

- **solar_reduction `factor` is the usable fraction REMAINING** (80% reduction → 0.2),
  not the reduction amount. Confirmed against public sample ground truth.
- **Whole-hour windows are start-inclusive, end-exclusive** (1 PM→3 PM = [13,14]).
- **End-of-day neutrality fixes total grid energy** at `sum(demand) − sum(solar_used)`.
  The LP is therefore *degenerate* — many distinct schedules share the optimal cost.
  Judge scores validity + cost, not the action sequence. Our plans match the published
  references to the exact BDT (ratio 1.0000).
- Post-solve `_assert_plan_valid()` replays the returned plan through every constraint.
  If the LP says X but the plan says Y, we fail loudly instead of shipping a bad plan.
- `summary.py` is deliberately deterministic — using the LLM for the summary as well
  would violate the challenge's intent.

## Bugfix: Swagger UI showed "No parameters" with no input box

Reported by the user: opening `/docs`, `POST /optimize-energy` rendered **"No parameters"**
and no request-body box, so the endpoint was unusable from the browser.

**Root cause.** The route does `raw = await request.body()` itself, so it can map malformed
JSON to 400 instead of letting FastAPI's parser raise a 422 traceback. That raw-body read
makes the body **invisible to FastAPI's OpenAPI inference** — nothing to declare a body
from, so Swagger shows no editor. The runtime taxonomy was correct; only the docs were broken.

**Fix** (`app/main.py`): kept the raw-body parsing untouched, added `openapi_extra=
{"requestBody": {...}}` to the decorator with `schema=OptimizationRequest.model_json_schema()`
and `example=_sample_body()`. `_sample_body()` builds a valid 24-hour scenario (the exact
§07.4 example notes) and is now the single source for both Swagger and any future doc.

**Regression tests added** (`tests/test_api_e2e.py`, 12 → 15 tests):
- `test_openapi_declares_request_body_for_swagger` — requestBody present + required + has
  schema + has example. Guards against the box silently disappearing again.
- `test_openapi_example_is_a_valid_24_hour_scenario` — the example must satisfy
  `OptimizationRequest` outright; a pre-filled example that 422s is worse than none.
- `test_documented_example_round_trips_through_the_endpoint` — POSTs the example with
  `_post` stubbed to the ground-truth reading; asserts 200, 24 hours, and that
  `no_charge_window` actually reaches the schedule.

**Lesson worth remembering:** any FastAPI route that reads the raw body must declare
`openapi_extra.requestBody` or its Swagger UI is dead. My first version of the round-trip
test failed because it hit the live provider instead of the per-test `_post` stub — follow
the existing `_stub_post_factory` pattern in that suite.

**Verified:** e2e 15/15, LLM stage 14/14, samples 10/10 (ratio 1.0000); a real uvicorn
instance POSTed the documented example over HTTP and returned 200 with
`solar_reduction / no_charge_window / no_op`. README gained an "Interactive docs
(Swagger UI)" subsection.

## Two real bugs found once a live credential was available

The user dropped a real `GROQ_API_KEY` into `.env` mid-session, which finally exposed
problems that every stubbed test had been hiding.

### Bug A — `.env` was never loaded (documented quickstart was broken)

`app/config.py` read config with `os.getenv()` only. `python-dotenv` was pinned in
`requirements.txt` but **nothing imported it**, so a correctly-filled `.env` was silently
ignored and every request failed with "no LLM credential configured". The README even told
users to `export $(grep -v '^#' .env | xargs)` as a workaround — evidence the file was
known not to load.

Fix: added `_load_dotenv_once()`, called at import, resolving `.env` next to the project
root via `Path(__file__).resolve().parent.parent`. Critically it passes
**`override=False`** so a platform-injected variable (Docker `-e`, Render env) beats the
file — otherwise a committed `.env` could shadow a deployment secret. Import is guarded so
a missing optional dep degrades to "no .env support" rather than crashing.

### Bug B — the default model no longer exists on Groq

`llama-3.3-70b-versatile` returns `404 model_not_found`. Groq's current lineup (verified via
`GET /models`) is `openai/gpt-oss-120b`, `qwen/qwen3.8-27b`, `openai/gpt-oss-20b`,
`groq/compound`, `allam-2-7b`, plus whisper/prompt-guard models. No Llama model at all.

Fix: default is now `openai/gpt-oss-120b` in `config.py`, `.env.example`, `render.yaml`.
All three models were tested live and produce **exactly correct** first-attempt
interpretations. `qwen/qwen3.8-27b` is fastest (~0.9 s vs ~1.3 s).

**Groq retires models regularly — always verify before deploying:**
```bash
curl -s https://api.groq.com/openai/v1/models -H "Authorization: Bearer $GROQ_API_KEY"
```

### Quota, not a bug: 8000 tokens/minute

10 live cases back-to-back gives 6/10 — the rest fail with a controlled 422/500. Not an
interpretation failure: the free tier allows **8000 tokens/minute** and each request costs
~1500–2500 tokens (the system prompt documents all six directive types), so the bucket
empties after ~5 requests. Proven by re-running a "failed" case after a 65 s cooldown.

Fix: added `--delay SECONDS` to `run_public_samples.py`. `--delay 15` gives 10/10 live.
This is a provider-account limit, not an implementation defect.

### SECURITY — the live key was sitting in `.env.example`

`.gitignore` has `!.env.example`, so the template **is** committed while `.env` is not. The
real 56-char key had been pasted into the template at line 8 — it would have been published

Fixed (emptied to placeholders) and guarded by two new tests in `tests/test_config.py`:

  that flags its own fixtures trains people to ignore it. **Negative-controlled:** planting a
  realistic key fails the suite, removing it passes.
- `test_env_example_ships_only_placeholders`.

## Docker bug found and fixed: wrong apt package for the CBC solver

While statically verifying the Dockerfile I read the CBC binary's `DT_NEEDED` entries
directly. The Dockerfile installed **`libgomp1`** "because CBC needs OpenMP". That is
false:

```
$ strings pulp/solverdir/cbc/linux/i64/cbc | grep -E '^lib(stdc\+\+|gomp)'
libgcc_s.so.1
libstdc++.so.6        # <-- never libgomp
```

The real dependency is **`libstdc++6`**, and `python:3.12-slim` does **not** ship it.
Confirmed from the authoritative build source
(`docker-library/python/3.12/slim-bookworm/Dockerfile`): the runtime stage installs only
`ca-certificates`, `netbase`, `tzdata`, then runs `apt-get purge -y --auto-remove`, which
removes the `g++` toolchain that would have provided libstdc++.

**Impact:** the solver would fail to start inside the image. Since the Guide designates the
Docker image as the fallback path when the hosted endpoint is unavailable, this would have
lost both the fallback and its 4 rubric points — and it would only have shown up at
container runtime, never in local testing (Windows CBC is a different binary with different
deps).

**Fix:** `apt-get install libstdc++6 curl` (libstdc++6 pulls libgcc-s1 automatically).
Also corrected the wrong claim in the README, which repeated the libgomp1 story.

**New suite `tests/test_docker_contract.py` (9 tests)** — machine-checks what is verifiable
without a daemon: CBC exists in the wheel, every non-glibc library CBC needs is provided by
an installed package (with `TRANSITIVE_PACKAGES` so libgcc-s1 is accepted as a dependency of
libstdc++6), COPY sources exist, binds 0.0.0.0, honours `$PORT`, non-root, and no
build-arg/COPY secret leakage.

**Negative-controlled:** reverting the Dockerfile to `libgomp1` fails 2 tests; restoring
`libstdc++6` gives 9/9. Re-verify after a pulp upgrade with:
```bash
strings <pulp>/solverdir/cbc/linux/i64/cbc | grep -E '^lib(stdc\+\+|gomp)'
```

**Lesson:** "never tested" is not "fine". Three separate bugs in this project were found by
checking a claim the code merely asserted — the `.env` not loading, the retired model, and
now the wrong solver library. Each had a confident comment next to it explaining behaviour
that was not real.

## Bug: /docs "Could not resolve reference: Invalid object key $defs"

User reported two Swagger UI errors while the API itself worked:
```
Resolver error at requestBody...properties.hours.items.$ref
  Could not resolve reference: Invalid object key "$defs" ... "/$defs/HourInput"
Resolver error at requestBody...properties.battery.$ref
  ... "/$defs/BatteryInput"
```

**Root cause.** `openapi_extra.requestBody...schema` was set to
`OptimizationRequest.model_json_schema()`, which is *self-contained*: Pydantic nests
dependent models under a schema-local `$defs` and points at them with the
**document-root-relative** pointer `#/$defs/HourInput`. That only works if the schema
sits at the document root. Inlined under `requestBody` it is one level down, so
Swagger resolves against the root, finds no `$defs`, and errors. Proved it: the served
document's root keys are `['components','info','openapi','paths']` — no `$defs` — and
both pointers failed to resolve.

**Fix.** `_inline_schema_for_swagger()` rewrites `#/$defs/X` → `#/components/schemas/X`
recursively and pops `$defs`; a custom `app.openapi` (via `get_openapi`) merges the
nested `HourInput`/`BatteryInput` definitions into `components/schemas` so the rewritten
refs land on real objects. All 6 refs in the document now resolve.

**Rejected approach — important.** Declaring a real `Body(...)` parameter also makes the
docs work and is the "obvious" fix, but FastAPI then validates the body *before* the
handler runs, turning malformed JSON and empty bodies from **400 → 422** and breaking the
spec's error taxonomy. Confirmed by reverting: 5 tests failed, including
`test_malformed_json_returns_400`. So the raw-body read + `openapi_extra` design must stay.

**Why the old tests missed it.** `test_openapi_declares_request_body_for_swagger` asserted
the schema *exists* — it did; only its internal pointers were dangling. Existence is not
reachability. New `test_openapi_request_body_schema_refs_all_resolve` walks every `$ref`
in the document and resolves it pointer-by-pointer (strict, mirroring Swagger's resolver),
plus asserts `HourInput`/`BatteryInput` are in `components/schemas` and that `hours.items`
resolves to an object with the four expected fields.

**Negative-controlled.** Reverting the one `schema=` argument makes the new test fail with
exactly `#/$defs/HourInput` and `#/$defs/BatteryInput` — the two refs from the report.

**Verified:** 49 tests pass (was 48), 10/10 samples ratio 1.0000 over real HTTP, `/docs` and
`/openapi.json` both 200, malformed JSON and empty body still 400, `$defs` correctly absent
from the document root, `HourInput`/`BatteryInput` present in `components/schemas`.

### The two real bugs the browser found (static analysis could not)

1. **Duplicate `id="notes"`** on both `<h3>` and `<textarea>`. `getElementById` returns the
   first match, so the code read the heading. Symptom was
   `page.inputValue: Node is not an <input>, <textarea> or <select>`. Fixed by renaming the
   heading to `notes-heading`; guarded by `test_no_duplicate_element_ids`.

2. **30px horizontal overflow at 390px, only AFTER a run.** Both `.panel`s computed to 407px.
   Root cause: a block-level grid item has `min-width: auto`, and the six-column schedule
   table's column widths shrink *below their min-content width*, so the table's min-content
   (420px) propagated up through `.table-scroll` -> `.panel` -> `.layout` and stretched the
   whole grid past the viewport. Fixed with `min-width: 0` on `.layout` and `.panel`, plus
   explicit column budgets on `table.plan` (`min-width: 30rem`, `white-space: nowrap`,
   `.num { width: 5.4rem }`) so the table overflows its scroll container instead of the page.
   Isolated by hiding one candidate descendant at a time and re-measuring `scrollWidth`.
   The harness now names the offending elements on failure instead of printing a bare pixel count.

### Method notes worth reusing

- **A stale server on the port is the single most misleading failure mode here.** An old
  `python.exe` from an earlier revision was still on :8000, serving the *pre-routing-change*
  JSON at `/`. Always confirm the revision before trusting any result:
  `curl -s $BASE/api` must contain `"ui":"/"`. Under Git-Bash, `taskkill` with a `//F` flag
  misparses; killing a PID is more reliable through the PowerShell tool than Bash.
- **A grid-item min-width bug only reproduces with the result panel rendered.** The bare page
  measured a clean 390. Any layout check must run after the dynamic content exists.
- **Docker ships the UI only because `COPY app ./app` happens to include `app/static/`.** That

## Paste-a-whole-request-JSON panel (judge-facing)

Requested so a judge with their own scenario is not forced to retype it into 72 fields.
Full-width panel at the bottom of the page with six controls: Load JSON, Optimize this JSON
(bypasses the form, POSTs the pasted object verbatim), Fill the form (pours the pasted values
into the visible inputs so every cell is editable), Paste a sample request, Clear, and a
normalised read-only preview.

Client-side `validateRequestObject()` mirrors the structure of `app/models.py` and reports the
first problem by name, so a mistake yields `"hours" must have exactly 24 entries (got 23)`
instead of a bare `HTTP 400`. Refactored `run()` into a shared `postRequest(payload, btn)` so
the form and the paste panel cannot drift in how they report failures.

**Unknown keys are checked FIRST, before the field checks.** A typo like `noets` for
`operator_notes` otherwise gets reported as the *missing* field, sending the reader to the
wrong place. Caught by the browser harness, which initially constructed its typo fixture by
deleting the real key and adding a stray one.

**Client validation direction matters.** The client may be stricter than the server, never
looser: telling a judge "this looks fine" and then returning 422 is worse than no client
validation. `test_paste_validator_output_passes_the_real_model` feeds everything the client
accepts through `OptimizationRequest.model_validate`.

### V8 JSON error messages are inconsistent — do not fake a position

`Unexpected token '…'` carries **no offset** (tested across trailing comma, unquoted key,
single quotes, truncated, Python `None`); the "Expected …" family does, sometimes already
formatted as `(line L column C)`. There is **no way to recover the offset** by re-parsing
prefixes: a prefix of a valid-but-truncated object is itself invalid (`{` is already a parse
error), so a prefix scan reports the start of the input, not the fault. My first attempt did
exactly that and pointed readers at line 1 column 1. Final behaviour: show the engine's own
message; append line/column only when it gave an offset, and never twice; otherwise state the
line count and suggest checking the closing braces. The harness asserts the position appears
at least once and **not twice**.

### Testing the validator without a browser

`validateRequestObject` lives inside an IIFE and touches the DOM, so the Python test extracts
the function by brace-matching and `eval`s it in Node with `MAX_NOTES` injected. Two traps:

- **Pass paths via the environment, not argv.** With `node -e <script> a b`, `process.argv`
  indices shift (`argv[0]` is the executable, not the script), which silently fed the JS path
  into `JSON.parse`. Env vars are unambiguous in both `node file.js` and `node -e` forms.
- **`JSON.stringify(…, null, 2)` is multi-line**, so `stdout.splitlines()[-1]` grabs only `}`.
  Parse the whole stdout when the JS is pretty-printing.

### Recovering from a self-inflicted `git checkout` (do not repeat)

`git checkout -- app/static/app.js` to undo a negative-control patch reverted the **whole
feature**, because HEAD (`a0461c1 "Frontend added"`) predates this session's paste work — the
user had committed the earlier frontend. Recovery: the pre-patch copy was still in `/tmp`,
restored by `cp`, then the single negative-control line was reverted by targeted string
replace (asserting exactly one occurrence). **Lesson: to undo a negative-control edit, keep the
backup and reverse the exact string — never `git checkout` a file whose uncommitted work spans
more than the patch.** The stale copy also came from the *previous* negative control, so the
second patch's anchor was gone; the failed assert is what surfaced it.
